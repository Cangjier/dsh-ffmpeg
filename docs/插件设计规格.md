# dsh-ffmpeg 插件设计规格

本文回答的是**为什么这样做**：边界画在哪里、哪些决定必须在纯函数里做、哪些数字有资格出现在结果里，
以及这个插件明确**不做**什么。使用方式看 [README](../README.md)，参数细节看
`ffmpeg_guide {action:"action", actionName:"…"}`。

---

## 1. 要解决的问题

ffmpeg 全能、稳定、无处不在，但直接用它做自动化有四类反复出现的失败：

1. **命令被二次解析**。把参数拼成一个字符串再交给 shell，中文名、空格、引号就变成语法。
2. **失败不像失败**。`-nostdin` 却忘了 `-y`，ffmpeg 会问一个没人看得见的问题然后退出 1；
   退出码 0 也可能是零字节文件、没有音频、时长少了一半。
3. **能力假设**。「Unknown encoder 'libx264'」「No such filter: subtitles」出现在一次长解码**之后**，
   而不是在「这台机器能不能做这件事」的时候。
4. **破坏性操作**。`ffmpeg -i a.mp4 … a.mp4` 会先清空输出再读输入——源文件原地消失。

第一条用「永远传数组」解决，第二、三条用「动手前问能力、写完后重新测量」解决，
第四条用「默认拒绝」解决。剩下的，是把一件需要几十个参数的事情，拆成一组**参数少到不可能搞错**的动作。

## 2. 分工

| | 谁 |
| --- | --- |
| 要什么、够不够好、这段录像在讲什么、下一步做什么 | **DSH** |
| 同样的输入给出同样的输出；每个数字都能追到测量 | **本插件** |

因此本插件里没有任何一处「猜」：没有判断「这个结果够不够好」的阈值分支，没有「大概是要这个」的默认，
也没有把不确定的东西说成确定的措辞。所有不确定都以 `null` + 原因的形式出现。

## 3. 表面：为什么是 8 个工具而不是 30 个

每个工具的 JSON Schema **每一轮都占上下文**。30 个扁平工具意味着 30 段描述常驻，而且互相重复。
所以表面这样切：

- **按作业分组，用 `action` 分派**：`ffmpeg_convert` 一个工具承载 7 个转换动作；
- **文档只有一个来源**：`src/tools/registry.mjs` 同时生成 schema 描述与 `ffmpeg_guide` 的内容，
  一个 action 在一处有、另一处没有就是**加载期报错**，而不是一份没人察觉的缺失文档；
- **常驻的只有一行**：每个 action 在 schema 里只留「做什么 + 需要什么 + 什么时候用」，
  返回形状、成本、坑、示例都放到 `ffmpeg_guide {action:"action"}`；
- **action 名在全局唯一**：`ffmpeg_guide {action:"action", actionName:"transcode"}` 接收裸名字，
  两个工具都叫 `audio` 就会歧义，所以录音那个叫 `microphone`。

`ffmpeg_run` 是刻意的逃生舱。结构化动作覆盖不到的事（比如某个滤镜组合）不该逼调用方去写脚本，
但同时它必须比 shell 更安全：参数是数组、执行前有 `check` 说明会发生什么、执行后测量产物、
输出是输入时**拒绝执行**（不是给个警告然后照做）。

## 4. 内核切分：plan 与 execute

`src/core/media.mjs` 里每个动作都拆成两半：

- **plan**（纯函数）：拿请求，返回确切的 `argv` 数组、说明、以及调用方该期待什么。
  不碰文件、不起进程，因此可以在没有 GPU、没有素材的情况下测试。
- **execute**：按顺序跑每一遍，失败时删掉半成品，成功之后**重新探测写出来的东西**。

稳定性就住在这个切分里。上面第 1、4 类失败、`.mp4` 名字配 `.mkv` 封装、缩放后高度变成奇数、
流复制切在没有关键帧的位置——全部在纯的那一半被决定，便宜、可测、不会漏。

`execute` 里还有一条**不变量检查**：计划声明了输出，但参数列表的最后一项不是它，就直接报内部错误。
ffmpeg 9 对「输出文件之后还有选项」是硬报错，而一个少写了输出路径的计划会得到一个空文件加一句
`Trailing option(s) found in the command`——这正是「只检查参数的测试」会漏掉的那一类 bug。

## 5. 稳定性清单

每条都对应实现与测试；列在这里是为了让「更稳」这句话可以被核对。

| 失败现象 | 措施 | 测试 |
| --- | --- | --- |
| 中文/空格/引号被二次解析 | 参数永远是数组；`longPath()` 统一给出 ffmpeg 能开的绝对路径 | `inspectArgs`、`escapeOptionValue` |
| ffmpeg 问了看不见的覆盖问题然后退出 1 | ffmpeg 永远自带 `-hide_banner -nostdin -y`；调用方重复给会被去掉并告知 | `run` 的受管选项、`ffmpeg_run check` 的 warnings |
| 输出随流顺序漂移 | 永远显式 `-map 0:v:0? -map 0:a:0?` | `transcodePlan` |
| JS 缓冲与 ffmpeg 尺寸差一像素 | 分析尺寸在这里算好（`fitSize`）再显式 `scale=W:H`，绝不用 `-2` 或滤镜表达式 | `fitSize`、`loadRgb` 的长度断言 |
| 退出码 0 但不是要的东西 | 每次写完 `verifyOutput`：流类型、字节数、时长容差 | 每个 `ffmpeg_convert` 测试都断言 `files[0].ok` |
| 半成品冒充交付物 | 失败即删输出与编号帧；`.part` 完成后才改名 | 「失败不留半成品」 |
| 输出就是输入，源文件被清空 | `assertSeparate()` 默认拒绝；`analyze` 发现交付路径会撞输入时自动改名并说明 | 三处拒绝测试 + 原地分析测试 |
| 几个 1080p 同时编码 | 信号量限制并发（默认 2），短只读调用绕过队列 | `ffmpeg_env probe` 报告并发值 |
| 「Unknown encoder」出现在长解码之后 | 动手前 `caps` + `checkNeeds`；缺编码器/滤镜直接拒绝，缺硬件加速只降级 | `checkNeeds`、各 action 的 preflight |
| ffmpeg 9 的 `-filters` 标志列宽度与表头不一致 | 按行结构解析（首列若是 `[A-Z.]{1,6}` 就当标志列），不假设宽度 | `parseListNames` 的四种格式 |
| 挂住的 ffmpeg 让 agent 不返回 | 每个进程都有超时；进度用 `-progress pipe:1` 解析；超时杀进程并报「超时」 | 超时路径（`run`） |
| `concat` 在输入之间无法重配置 | 强制统一画布，按比例缩放 + 补黑边（不拉伸） | `concatCanvas`、端到端拼接不同尺寸的两段 |
| 200MB 下载断在 90% | `.part` + `Range` 续传；服务器忽略 Range 时截断重来 | `downloadFile` 的结构（`net.mjs`） |
| 半个压缩包被当成品 | 先校验 SHA-256/report，再解压；解压校验未压缩大小 | `extractBinaries` 的四种拒绝 |

## 6. 语义结构文档

`ffmpeg_semantics {action:"analyze"}` 写出 `<名字>.semantics.json`，`version: 1`。
字段含义改变时**升版本**，加字段不升。

```
version, generatedAt
source      探测到的源文件事实（时长/尺寸/帧率/编码/问题列表）
options     这一次实际生效的阈值（不是默认值表，是这一次用的值）
analysis    分析是怎么做的：模式、分析尺寸、帧率、解码帧数、耗时、解码错误
providers   谁提供了文字、谁提供了分割（含不可用的原因）
timeline    段数、时长、解码帧数、分析尺寸与帧率
segments[]  每段：起止、起止原因与边界差值、运动量、类别与判定依据、
            关键帧、区域矩形、标签占比、主色、文字（含 provider 与逐行坐标）
structure   段落类别的汇总、外观标签均值、区域词表、规则原文、关键词、有文字的段数
outputs     结构 JSON / 关键帧目录 / 联系表 / 交付视频（含 ok 与 problems）
notes       这一趟里所有值得说的（跳过、降级、失败与原因）
```

设计选择：

- **`options` 是这一次的值**，不是默认值表。看到 `sceneThreshold: 8` 就知道它真的用了 8。
- **`startScore` 与 `sceneScore` 分开**。一段有两条边界，用一个数字会在一处表示「起点」、
  在另一处表示「终点」，而文件结尾根本没有差值可言（`null`）。
- **缺席永远是 `null` + 原因**。「没有 OCR」和「屏幕是空的」是两件不同的事，不能长成同一个样子。
- **`kindEvidence` 带规则原文**。类别是规则算出来的，读的人应该能当场核对，而不是只能相信。

## 7. 规则表（全部写死，可核对）

**外观标签**（`regions` 的 `label`，按块判定后并成矩形）：

| 标签 | 判定（按优先级） |
| --- | --- |
| `dark` | 亮度标准差 < 4 且平均亮度 < 48 |
| `flat` | 亮度标准差 < 4 |
| `text` | 边缘像素占比 ≥ 9% 且平均饱和度 ≤ 0.22 |
| `picture` | 平均饱和度 ≥ 0.18 |
| `texture` | 边缘占比 ≥ 2.5%；其余有结构但不彩色的区域 |
| `texture`（弱） | 上面都不满足：有结构但很安静，`score` 记 0.1 |

**运动档位**（`motion.level`，输入是平均亮度差 MAD，0–255）：
`static < 0.5 ≤ low < 3 ≤ moderate < 10 ≤ high`

**段落类别**（`kind`）：

| 类别 | 条件 |
| --- | --- |
| `document` | static + 有文字 |
| `still_image` | static + 图像占比 ≥ 25% + 无文字 |
| `idle` | static 且无文字；或 low 且无文字且非图像 |
| `typing` | low + 有文字 |
| `scrolling` | moderate + 有文字 |
| `video_playback` | moderate/high + 图像占比 ≥ 25% |
| `animation` | moderate/high 且非图像 |
| `unknown` | 证据不足 |

「有文字」= OCR 行数 > 0 或 `text` 标签占比 ≥ 5%。

**关键词**：拉丁词按非词字符切分、小写、去停用词与纯数字；中日韩按 2–4 字 n-gram 枚举，
若某个更长的 n-gram 包含它且出现次数不少于它，则丢掉它（`语义` 被 `语义分割` 吸收）。
按出现次数排序，附所属段号与首次出现时间。**这是词表，不是摘要。**

## 8. 诚实边界

- **区域标签是外观分类，不是语义分割**。它说的是「这里细密高频、低饱和」，不是「这里有一个按钮」。
  结果里 `providers.segmentation.appearance` 明说了这一点，`regionVocabulary` 给出每个标签的定义。
- **段落类别是规则，不是理解**。规则原文随结果返回（`structure.kindRules`），输入只有实测到的运动量与外观占比。
- **整条链路里唯一的学习模型**是 `segmentation:"salient"` 时向同级 `video-factory` 要的那张 U²-Net 掩码，
  输出里标明 `provider`，不可用时说明原因并退回外观分类。
- **OCR 是线索，不是数据**。Windows 自带识别在小字混排上会读错（实测把 `ALPHA 111 ffmpeg` 读成
  `ALP 1 ffmpeg`），所以 provider 与逐行置信度都在结果里，`notes` 里也写明。
- **`keywords`、`kind`、`regions` 都不构成「这段录像在讲什么」的结论**。它们是给 DSH 做判断用的测量值。

## 9. 与兄弟插件的边界

- **声音**的制造、修复、测量属于 `dsh-video-audio`（`audio_*`）。本插件只做「取出来 / 换掉 / 按测量值归一化」。
- **成片流程**（素材 → 场景 → 拼接 → 交付）属于 `video-factory`（`video_*`）。
  本插件的 `analyze` 只把录像读成结构，剪不剪、怎么讲是 DSH 的决定。
- **文字定位与点击**属于 `dsh-ocr` / `dsh-computer-use`。

可选集成一律**按路径动态 import**，不写进 `package.json` 的依赖：

```js
await import(pathToFileURL(join(root, 'dsh-ocr', 'src', 'core', 'index.mjs')).href)
```

原因是 `link:` 安装的插件解析的是自己的真实目录，而不是 profile 的 `node_modules`，
用包名 import 会在最需要它的时候失败。找不到就从候选列表里报出「找过哪些位置」，
而不是抛一个没有上下文的模块错误。

## 10. 测试策略

三层，都不需要联网：

1. **纯函数**（`tests/core.test.mjs`，47 个）：参数构造与顺序、尺寸算术、时间轴状态机、
   区域合并的不重叠性、关键词前缀吸收、能力解析、压缩包拒绝路径、语义规则表。
2. **工具面**（`tests/plugin.test.mjs`，13 个）：注册结果、文档覆盖（schema 与 registry 双向一致）、
   action 名唯一、schema 闭合、未知 action 被拒、guide 能为每个工具与 action 作答、
   playbook 里的每一步都调用真实工具。
3. **端到端**（`tests/ffmpeg.test.mjs`，25 个）：真 ffmpeg，驱动**注册后的工具定义**而不是内核，
   因此参数校验、能力预检、计划、执行、产物的重新测量都被覆盖到。
   素材由 `lavfi` + `drawtext` 现造（`tests/helpers.mjs`）：一段彩色运动画面 + 文字、
   一段纯暗画面 + 另一段文字、一条音轨，正好是本插件必须区分开的三种东西。

没有 ffmpeg 的机器上第三层自动跳过并说明原因，而不是失败。
`tmp/` 下的三个手跑脚本（`smoke` / `analyze-smoke` / `record-smoke`）打的是人眼要看的东西：
注册了什么工具、用的是哪份 ffmpeg、结构长什么样、真录一段屏幕会得到什么。

## 11. 已知限制与未做的事

- **不做音频分析**（响度、噪声、语音区间在 `dsh-video-audio`）；本插件只做音频的搬运与归一化。
- **不做逐帧分割**。区域分割是按段的代表帧做的；要每帧掩码请用 `video-factory` 的 matte 序列。
- **不做 GPU 检测的自动降级**。`caps` 会报出可用的硬件编码器，但选哪一个由调用方决定，
  因为「自动挑一个更快的」会让同一份计划在两台机器上产出不同文件。
- **不做 VFR 的精确时间轴**。分析按固定帧率采样（默认 4fps），可变帧率素材的切点精度受此限制，
  已在 `probe` 的 `problems` 里提示。
- **不做网络流**。输入都是本地文件；`pipe:`、`rtsp://` 之类没有专门支持（`ffmpeg_run` 仍可用）。
- **不保证跨 ffmpeg 大版本的同字节输出**。参数与流程是确定的，编码器本身不是；
  要可复现就用 `ffmpeg_setup {action:"install"}` 固定住那一份构建。
